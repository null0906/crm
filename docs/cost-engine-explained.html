Pillar 4 · Engagement Pricing

How the cost engine works

Turning a scoping conversation into a delivery cost, a defensible price, and a number you can still reproduce eighteen months later when the client disputes the invoice.

Seccomply Client Platform Branch: feat/cost-engine-catalog-estimates Currency: INR

The shape of the answer

Every engagement we cost comes down to one sentence: a team of certain people, for a certain number of weeks, plus the things that aren't people, plus a percentage for the work we pay for but can't bill.

per resource, per week base + seat + support = loaded weekly cost per engagement ( Σ(loaded weekly × weeks × headcount) + non-labour + custom ) × (1 + GNR%)

That is the whole model. Everything else in this document is about where each of those numbers comes from, who is allowed to change it, and how we prove afterwards what it was at the moment we quoted.

Why resource-weeks, not hours

We do not track hours and we are not going to start. We staff engagements by putting named people on them for stretches of calendar time. The unit that matches how we actually work is the resource-week: one person, for one week.

Two analysts for ten weeks is twenty resource-weeks — not ten. That distinction matters because it is what per-resource-week costs multiply against, and getting it wrong halves or doubles the estimate.

Stage 01

The baseline — what this service normally takes

A baseline is our institutional memory for a service line, written down as a team shape. Not a price, not a duration — a list of roles, how many of each, and for how many weeks.

Baselines live under Settings → Effort Catalog. Each one is scoped to a service line and a segment, so SOC2 / mid-market and SOC2 / enterprise are separate records with separate shapes.

Delivery rolePeopleWeeksResource-weeks

Baseline effort24

Baselines are versioned, never edited

When you correct a baseline you press Revise, which writes version N+1 and retires version N. It does not overwrite anything.

This is deliberate and it is the single most important property of the whole catalog. An estimate stores which version it was built from. So an estimate you built in March still resolves the March baseline in September, after the shape has been corrected twice. Nothing you have already quoted can move underneath you.

Judgement-based until proven otherwise

Every new baseline starts flagged judgement-based with confidence: low and a sample size of zero. That flag is not a formality — any estimate built on a judgement-based baseline carries a warning saying the numbers are somebody's opinion, not measured delivery.

The flag can only be cleared once the sample size is above zero. The system refuses to let you mark a baseline as evidence-backed while claiming zero delivered engagements behind it.

Read this one carefully

We do not yet capture delivered effort, so nothing raises sample size automatically. Today every baseline is judgement-based unless a human sets the confidence by hand — and a human setting it by hand is still judgement, just with the warning turned off. See what isn't built yet.

Stage 02

Scoping drivers — how this one differs

The baseline says what a typical engagement takes. Stage 2 asks what makes this one bigger or smaller. That is the scoping questionnaire, and each question is a sizing driver.

Drivers are configured under Settings → Effort Catalog → Sizing Drivers. A driver is a question that genuinely changes how much work an engagement is. Anything that doesn't change effort doesn't belong here.

Two kinds of question

Choose one
A fixed list of answers, each with its own weight. Regulatory regime: single jurisdiction (×1.0) / multi-jurisdiction (×1.3).
A number
A rate per unit, charged only beyond a threshold. Subsidiaries in scope: +10% for each one beyond 1. Units at or below the threshold are already priced into the baseline, so they cost nothing extra.

What a driver changes matters commercially

Every driver declares whether it adds weeks, adds people, or both — because those are not the same money.

  • Adds weeks — same team, longer engagement. Three cloud environments the same two analysts have to work through in sequence.
  • Adds people — same duration, bigger team. A deadline that cannot move, so you parallelise.
  • Both — the effect splits across the two axes.

A both driver contributes the square root of its weight to each axis. A 1.44× driver contributes 1.2× to weeks and 1.2× to team — and 1.2 × 1.2 = 1.44, the effect it declared. Applying the full 1.44 to both axes would produce 2.07×, silently squaring the driver's stated effect.

The composition ceiling

Drivers multiply. That is the right model — a large client and multi-jurisdiction and no existing controls really is worse than any one of those alone. But multiplication has no natural stopping point. Four drivers at 1.4× each compose to 3.8×, and nobody chose 3.8. It fell out of four answers that each looked reasonable in isolation.

So there is a ceiling, set under Sizing Drivers → Composition ceiling. Anything above it is capped — and the estimate says so, in three places: an amber panel in the questionnaire naming both the raw and capped figures, a warning on save, and a capped flag stored with the result.

If Meridian had also been rushed

Add a fourth driver — Timeline: compressed, ×1.45, adds weeks:

weeks = 1.20 × 1.45 × 1.1402 = 1.9839 team = 1.4252 ───────────────────────────────────── raw = 2.8275× ← above the 2.50 ceiling scale = √(2.50 / 2.8275) = 0.9403, applied to both axes weeks = 1.8655 team = 1.3402 total = 2.5000× ← capped, and flagged

Note the cap scales both axes rather than clamping the total. Weeks and team are used separately in the next stage, so clamping only their product would leave the two inconsistent with the answer.

How to set the ceiling

Set it to the largest multiple of a standard engagement you would still quote from a template. Beyond that you are not sizing a template any more — you are scoping a different job, and the estimate should be built from scratch. Too low and every complex deal caps, so the warning becomes noise people click past. If no ceiling is configured, the engine defaults to 2.5× and warns you that it did.

Changing a weight can't move a quote you've sent

Unlike baselines and rates, driver weights are edited in place — there is no version history. That is safe for exactly one reason: every estimate stores the multiplier it actually used at the moment its questionnaire was answered. Change a weight today and it affects the next estimate scoped, never one already built.

Deleting an answer works the same way. Estimates that used it keep their multiplier; they lose only the record of which label was chosen.

Each answer also records who supplied it and how sure they were. When an estimate turns out badly wrong, that is the trail back to the conversation that caused it.

Stage 03

Sizing the team

Now the baseline shape gets stretched by the two multipliers. Headcount goes up by the team multiplier, weeks go up by the weeks multiplier.

There is one wrinkle: you cannot staff 2.85 people. Headcount has to round to a whole number, and rounding it naively would silently change the total effort by up to half a person per line.

So the engine rounds headcount, then folds the rounding residue back into weeks. Total effort comes out exactly equal to baseline effort × multiplier, every time.

Re-answering the questionnaire re-sizes the team from the baseline again — which means manual edits to the team shape are discarded. The builder warns before doing it, but it is worth knowing: scope first, hand-tune second.

Stage 04

Pricing the people

Every resource costs three things per week, and they are kept separate because they answer to different people and move on different cycles.

base
Salary cost. What the person is paid, expressed weekly.
seat
Desk, laptop, licences, insurance — the cost of having them employed at all.
support
The share of management, admin and internal function that delivery carries.
loaded weekly cost = base + seat + support line total = loaded weekly × weeks × headcount

Most-specific-wins

Each of the three components can be set at three levels. When the engine needs a number it takes the most specific one available:

Scope resolution
ScopeSet onBeats
employeeOne named personrole, default
roleAll Security Analystsdefault
defaultCompany-wide fallback—

In practice you set seat and support once at company default and almost never touch them, set base per delivery role, and add employee-scope rows only for people whose cost is genuinely out of line with their role.

The estimate records which scope each figure came from, so any number on screen can be traced to the row that produced it.

If a rate is missing

The engine treats it as zero and raises a warning naming the role and the component. It does not refuse to compute. That is a deliberate trade — a blocked estimate teaches you nothing, an obviously-too-cheap one with a warning attached tells you exactly what to go and configure. But it does mean an ignored warning produces a quote that undercharges.

Rates are effective-dated

A rate row carries an effective from date and an optional effective to. Raising a salary does not overwrite the old rate — it closes it and opens a new one.

Every estimate has an as-of date, and rates resolve against that date. An estimate dated March resolves March's rates forever, no matter what has happened since. This is what makes an old quote defensible rather than merely archived.

The database enforces that only one open-ended row can exist per scope and component, because two would make rate resolution non-deterministic — the same estimate could compute differently on two consecutive page loads.

Blended or named

An estimate is costed one of two ways, and it is a per-estimate switch:

  • Blended — everyone in a role costs the role rate. Right for early-stage deals where you don't know who is available.
  • Named — specific people are attached to lines, and their employee-scope rates apply. Right when the team is decided and you want the real number.

Every figure is overridable

Any of the three components can be overridden on a single line of a single estimate. An override does not touch the rate table — it applies to that line only, and the estimate records that the figure was overridden rather than resolved.

Stage 05

Everything that isn't people

Two kinds of line, and the difference between them is commercial, not technical.

Non-labour

Tooling licences, travel, third-party testing, certification fees. Each line is marked either pass-through or not.

  • Pass-through — quoted to the client at exactly what it cost us. Never marked up. Airfare, statutory fees, anything where a markup would be indefensible if the client saw the invoice.
  • Marked up — carried like any other cost and priced into the engagement.

Both are tracked separately all the way through, so the split is visible on the breakdown rather than buried in a single total.

Custom lines

The escape hatch. Anything an estimator needs that isn't in the model, on one of two bases:

engagement
A flat amount, once.
per_resource_week
Multiplied by total resource-weeks across the whole team.

The per-resource-week basis is the one that scales properly with the size of the job — an evidence-platform seat, a per-head client security clearance.

Stage 06

GNR — the work we pay for but can't bill

Gross Non-Recoverable. A single percentage uplift covering the delivery cost that exists but never appears on an invoice:

  • Bench time — the gap between one engagement ending and the next starting.
  • Rework — the second pass we didn't quote for.
  • Unbilled travel and admin — the hours that go into delivery but not onto a bill.

This is the number that separates an estimate that looks profitable from a business that is profitable. Costing an engagement at the raw sum of its people assumes those people are billable 100% of the year. Nobody is.

Two bases

total
Applied to labour + non-labour + custom. The default.
labour_only
Applied to labour alone. The stricter reading: bench time is a property of employing people, and a tooling licence doesn't sit on the bench.

Meridian · GNR at 18%, basis: total

basis 36,02,060 GNR @ 18% 6,48,371 ────────────────────────────── total delivery cost 42,50,431 on labour_only the basis would be 33,96,900, GNR 6,11,442, total 42,13,502 — about ₹37,000 less

GNR policies are versioned and effective-dated, same as rates. An estimate stores the policy, the rate and the basis it used, so a historic quote reproduces under the GNR that applied to it — not today's.

If no policy is configured

GNR is applied at 0% with a warning. An estimate with no GNR policy is understating true cost by whatever the real figure should be — which for most consulting businesses is somewhere between 15% and 25%. Setting this is the highest-leverage configuration decision in the system.

Stage 07

Price and margin

The engine has now produced total delivery cost. It has not produced a price, and it never will.

The principle

Cost sets the floor. The market sets the price. Margin is advisory throughout — the system tells you where you stand and does not decide for you.

Margin is calculated on price, the consulting convention:

margin % = (price − cost) / price × 100

Note this is not markup. A 40% margin is a 67% markup. Mixing the two up is how a quote that looks healthy turns out not to be, so the system consistently uses margin-on-price and labels it that way.

Targets and floors

Under Settings → Cost Model → Margin Targets you set a target per service line, with an optional floor beneath it. A company-wide default catches anything without its own target.

Target
What you're aiming for. Drives the suggested price the builder shows.
Floor
Below this, the builder warns loudly. Optional — no floor means no warning.

The database refuses a floor above its target, since that would warn on every compliant price.

Meridian · quoted ₹62,00,000 against a 38% target, 30% floor

Suggested price is cost / (1 − 0.38). The deal is under target but above floor: worth a conversation, not a refusal. That is exactly the case the tool exists to surface.

The floor does not block approval

A price below the floor produces a warning and nothing more. Blocking approval would need an exception-approval trail — who overrode it, on what authority, when — and that does not exist yet. A block with no way to escalate past it just teaches people to work around the system.

Scenarios

Any estimate can be duplicated into a fresh draft, which copies the team, the cost lines and the questionnaire answers, and records what it came from. Build the aggressive version and the safe version side by side, then compare them on cost, multiplier, price and margin in one view.

Freezing an estimate

A draft recalculates every time you open it. That is correct while you are still working on it, and completely wrong once you have quoted a client.

So approving an estimate freezes it. The full breakdown — every resolved rate, every line, the GNR policy, the multiplier — is written to the estimate as a snapshot, and the record becomes immutable. Opening it afterwards returns the snapshot rather than recomputing.

Three things enforce this, deliberately layered:

  1. The builder's write controls disappear on a non-draft estimate.
  2. Every mutating operation on the server checks the status first and refuses.
  3. A database constraint refuses to store an approved estimate that has no snapshot and no freeze timestamp — so a status change cannot skip the freeze even if the application code is bypassed entirely.

Want to change an approved estimate? You duplicate it. The original stands as the record of what was actually quoted.

Why this matters commercially

An estimate that could be edited after approval would destroy the only signal that tells you your estimates were wrong. If the number can move retroactively, you can never compare what you quoted against what it cost — and estimation never improves.

What reproduces, and what doesn't

Everything that goes into cost is frozen. The margin floor is deliberately resolved live, because it is a present-day warning threshold rather than part of the historical basis. If you raise the floor next quarter, last quarter's approved estimates will start showing as below it — which is the correct behaviour, not a bug.

Who can see cost

Cost rates are salary-derived. A base rate for a named person is that person's pay, expressed weekly. This is the most sensitive data in the platform and it is treated that way.

Granted to a person, not a job title

Financial access is a per-user entitlement, not a role permission. Being a sales manager does not grant it. It is switched on for named individuals under Settings → Users, and only a super admin can grant it — an entitled person cannot widen the circle. Every grant and revoke is audited with before and after values.

The entitlement is read live on every request, not from the login token. Sessions last seven days; a revoked entitlement stops working immediately rather than surviving until the token expires.

Default-deny redaction

There is one gate that every cost-bearing response passes through. It nulls a registry of known financial fields rather than accepting a per-endpoint allow-list — so a newly added cost field is protected the moment its name is registered, not whenever someone remembers to update a call site.

Margin is treated as cost, and this is not paranoia

cost = price × (1 − margin). Showing a margin percentage next to a visible price leaks the cost exactly as surely as printing it. Margin fields are therefore redacted alongside cost fields. Price is not — it is the quotable fact, the number the client is told, and anyone selling needs it.

The other surfaces

  • The AI assistant — cost-related keywords are blocked for users without the entitlement, and the underlying cost tables are unconditionally excluded from any generated SQL.
  • Reads are audited — every read of an individual cost rate is written to the audit log.
  • Reference data stays open — delivery roles, baselines and driver definitions are readable by everyone. Only money is gated. A salesperson can see that SOC 2 mid-market normally takes 24 resource-weeks without seeing what a resource-week costs.

Order of setup

The stages depend on each other, so configuration has an order. Skipping ahead produces estimates full of warnings:

  1. Delivery roles — nothing else can reference a role that doesn't exist.
  2. Cost components — company defaults for seat and support, then base per role.
  3. GNR policy — until this exists every estimate understates cost.
  4. Margin targets — at minimum the company-wide default.
  5. Composition ceiling — or accept the 2.5× default.
  6. Baselines and drivers — one service line at a time; there is a coverage view showing which lines have no baseline.

What isn't built yet

Stated plainly, because a founder deciding whether to rely on this needs to know where the edges are.

1 · Delivered effort is never captured

Nothing feeds actual delivery back into the catalog. Sample size stays at zero, so every baseline stays judgement-based unless someone sets confidence by hand. Until this closes, the catalog is a well-structured record of our opinions — which is genuinely better than a spreadsheet of the same opinions, but is not evidence.

2 · No exception-approval trail

The margin floor warns; it cannot block. Blocking needs a record of who authorised the exception, which does not exist.

3 · No automated test suite for the engine

The arithmetic was verified with throwaway scripts against a local database during development — which did catch two real bugs, including one that would have broken every multi-role estimate. But those scripts were not kept, and the repository has no committed tests covering cost computation. A regression here would be silent and expensive.

4 · Not yet exercised by a human

The estimate builder has not been clicked through end to end in a browser by anyone. It type-checks and builds; that is not the same as working.

5 · Older deal-amount masking not yet consolidated

Deal-value masking predates the cost engine and is still duplicated across seven files. The new gate does not yet cover them. Cost and margin are gated correctly; this is about tidying an older pattern before it drifts further.

What is solid

  • The arithmetic — the formulas above are what the code does, verified line by line against this worked example.
  • Reproducibility — effective dating, versioning and the approval freeze are enforced in the database, not just in application code.
  • The access gate — default-deny, read live, audited, with margin correctly treated as a route back to cost.
  • Every figure is overridable, and every override is recorded as an override.
